## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Outcome: a Target Range shot lands where the TV crosshair visibly was at release, not wherever the phone's own live aim happened to be.

Type: deliverable
Branch: CC-11.10/shot-uses-shown-aim

Root cause (found during the CC-3.24 owner replay, 2026-09-19): games/target-range/src/controller/aim.ts's shoot() sends channel.last("aim"), the phone's most recent live-streamed sample. But the TV's displayed crosshair (games/target-range/src/host/aim-playback.ts's createCrosshairPlayback) is a delayed, interpolated/predicted rendering (playbackDelayMs behind), built for the relay path's 4/s budget and reused for the direct link's smoothing. The controller's own comment says the shot should carry "the aim the TV was shown", but the code sends the live value instead, so the two mismatch whenever the aim was still moving at release.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria

- [x] #2 A unit or replay test proves the mismatch (moving aim, then release) and proves it's fixed

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Root cause: shoot() sent channel.last(\"aim\"), the phone's freshest live-streamed sample, while
the TV's crosshair (createCrosshairPlayback) renders a delayed+interpolated/predicted value,
AIM_PLAYBACK_DELAY_MS behind. The phone can't learn the TV's exact per-connection playbackDelayMs
(host-only tuning in apps/host/src/runtime/links.ts, outside this story's References, and games
must never branch on channel.path per the SDK contract) or a new wire message (also out of
References), so per the story's hinted direction (a): the controller now buffers the "aim" samples
that actually reach channel.stream (post move-threshold filtering, so it matches exactly what the
TV received) into a local SampleTrack, and at shoot() replays that track through the same shared
createPlayback the TV's crosshair uses, AIM_PLAYBACK_DELAY_MS behind, in a fresh (stateless)
Playback instance evaluated once at release. Both sides run the identical deterministic algorithm
over the same samples, landing on the same "shown" aim with no new message and no protocol change.
Files: games/target-range/src/controller/aim.ts (buffer + replay in shoot()),
games/target-range/src/host/aim-playback.ts (doc note only, no behaviour change -- it already takes
delayMs as a parameter), games/target-range/test/controller/aim.test.ts (updated the two tests that
hardcoded the old live-sample behaviour) and a new games/target-range/test/shown-aim.test.ts that
drives the real controller + the real host reducer + the real createCrosshairPlayback end to end and
proves the shot's aim lands on the exact point the TV was rendering, and that it differs from the
phone's stale live sample.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Fix delivered: controller buffers streamed aim samples locally and replays them through the shared createPlayback (@couchcade/game-sdk/input), AIM_PLAYBACK_DELAY_MS behind, at shoot() time -- matching aim-playback.ts's createCrosshairPlayback without a new message. games/target-range/test/shown-aim.test.ts drives the real controller + host reducer + createCrosshairPlayback end to end and proves the shot lands on the TV's rendered point, distinct from the phone's stale live sample. Note: exact per-connection playbackDelayMs (apps/host/src/runtime/links.ts: 180ms relay / ~33ms direct) isn't shared with the phone and games must not branch on channel.path (SDK contract), so the phone uses the shared generic AIM_PLAYBACK_DELAY_MS (250ms) constant both sides already use as the nominal delay. Follow-up if tighter per-connection precision is wanted: a host->phone playbackDelayMs message (protocol change, out of this story's References).

Round 1 reviewer verdict: block on AC1 -- the replay used the shared generic AIM_PLAYBACK_DELAY_MS (250ms) instead of the real per-path delay scene.ts's playbackDelayMsOf actually renders with (~33ms direct at 30Hz / 180ms relay, apps/host/src/runtime/links.ts). Fixed: shoot() now reads channel.path (public on InputChannel; read only to pick the matching delay, never to change what's sent) and computes shownDelayMs(path) mirroring links.ts's two constants. Widening ShotChannel to include "path" needed a one-line consequential fix in Controller.vue's no-op fallback channel. Tests updated to use the real shownDelayMs(path) and now cover both direct and relay paths (shown-aim.test.ts runs describe.each over both). Re-review requested.

Reworked ShotChannel.path to be optional (not a Pick-required field) so the fix stays inside aim.ts/aim-playback.ts/test/ -- avoids an out-of-References Controller.vue edit. Requesting round 2 review.

Round 2 reviewer verdict: PASS. Both acceptance criteria met, no scope violations. Advisory (non-blocking): (1) InputChannel.path's docstring in packages/game-sdk/src/contract/index.ts still says a game never branches on it -- this fix legitimately does, for playback-delay parity only, never to change what's sent; a follow-up could update that docstring. (2) shownDelayMs mirrors apps/host/src/runtime/links.ts's constants by hand rather than importing them (cross-package import isn't available given tier boundaries) -- could silently drift if the host constants change; a follow-up could centralize them in a shared package. Confirmed by reviewer: games/target-range/src/controller/Controller.vue has zero diff vs origin/main; 157/157 tests pass.
