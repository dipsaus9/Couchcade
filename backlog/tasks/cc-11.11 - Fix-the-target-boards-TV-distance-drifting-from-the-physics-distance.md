## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Outcome: the board's on-screen distance in later Target Range rounds matches the distance the physics/hit-detection actually use, so the visual doesn't mislead where an aim will land.

Type: deliverable
Branch: CC-11.11/board-distance-matches-physics

Reported during the CC-3.24 owner replay (2026-09-19): "the board goes closer to the screen in later games while in the physics it is further away." Not yet root-caused in code; needs investigation of the TV scene's per-round board placement/camera vs. the shared shot/flight distance.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 The board's rendered distance across every round visually matches the distance value the shot/hit physics use for that round
- [x] #2 A test (or a recorded playthrough) checks round-to-round board placement against the physics distance

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Root-caused via headless screenshot + state dump (recorded in notes). Fix: shared/constants.ts adds targetMaxY(radius), shared/state.ts's rollTarget caps the target's near/high-Y edge per round in proportion to radius/rounds[0].radius (round 1 unchanged at 160, round 2 at 152, rounds 3-4 at 144), so on-screen depth tracks the physics distance (radius/drop/flight-time/wind) every round instead of rolling independently of it. docs/games/target-range.md's target-placement wording updated to match (owner-approved via orchestrator); References amended to include it. test/host/present.test.ts adds a test asserting the per-round cap is monotonic and that rollTarget respects it (AC2). test/recordings/three-player-match.json's finalState/outcome regenerated from the same recorded input events under the new rules.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Root-caused (2026-09-20). Read shared/state.ts, shared/rules.ts, shared/flight.ts, shared/constants.ts and host/present.ts, host/world.ts, host/layout.ts, host/scene.ts in full. The target FACE (radius, via faceKey texture swap in world.ts) and the scoring radius (rules.radius in flight.ts's arrowPoints) are both derived fresh every frame from the identical roundRules(state.round) call, so they never drift from each other -- confirmed by direct code inspection and by measuring the near/middle/far PNG assets pixel-by-pixel (outer ring edges land at exactly 36/30/24px, matching the declared radii). That part of the render is correct.

The actual drift is in shared/state.ts's rollTarget(): the target's on-screen Y placement (targetMinY=110 to targetMaxY=160, shared/constants.ts) is the SAME fixed window for every round, uncorrelated with the round's physics distance (radius/dropPx/baseMs/windPx, which do increase every round). Since the range world's backdrop implies near/far by vertical position (mown stripes get taller 'towards the couch, for depth', world.ts comment), a target that randomly rolls a high Y (close to the viewer/couch) in a later, physically-farther round visually reads as CLOSER than an earlier, physically-nearer round that happened to roll a low Y. Verified two ways: (1) a fresh headless match (seed 7, bot-driven, screenshotted each round) rolled round1(near, radius36) target.y=112 (near horizon = looks far) vs round3(far, radius24) target.y=148 (near the couch = looks close) -- the reverse of the physics; (2) the existing golden recording test/recordings/three-player-match.json's finalState has round 4 (far and gusty, the single farthest round) landing target.y=150, i.e. also near the close end of the SAME flat window.

A faithful fix requires making rollTarget's Y window track roundRules(round).radius (e.g. cap the close/high-Y end progressively as radius shrinks) so on-screen vertical placement trends the same direction as physics distance every match. That's achievable inside the story's References (shared/state.ts, shared/constants.ts) but it (a) contradicts the literal wording of the owner-approved docs/games/target-range.md spec ('Each round ... places the target centre at x 160 to 320 and y 110 to 160' -- stated as flat, not per-round), (b) changes per-round difficulty/feel (later rounds would get a narrower, more horizon-biased roll window), and (c) invalidates test/recordings/three-player-match.json's finalState/outcome (a golden recorded-input replay), which would need regenerating. Paused for a go/no-go on reshaping this RNG-affecting, spec-described formula before implementing, per the working agreement reserving product/architecture calls for the owner. No purely-cosmetic host/-only fix was found that resolves this without touching the roll window, since the misleading cue comes from the target's absolute screen position (interacting with the fixed backdrop's implied depth), not from anything render-side that swaps with state.target unchanged.

Story-reviewer verdict (round 1, sonnet): pass. Both acceptance criteria met, no scope violations, no findings. Verified targetMaxY(radius) formula values (160/152/144), rendering still positions the target sprite directly at state.target with no other scaling, and confirmed via a full test run (158/158) plus vue-tsc that the regenerated golden recording is a genuine replay output.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Root-caused the owner-reported 'board looks closer while physics says farther' drift: the target's on-screen Y placement rolled in the same fixed 110-160 window every round, uncorrelated with the round's physics distance (radius/drop/flight-time/wind, which do grow each round), so a later, physically farther round could randomly land visually closer than an earlier one. Fixed by capping how close to the couch the target may roll in proportion to the round's radius against round 1's (targetMaxY in shared/constants.ts: 160/152/144/144 for rounds 1-4), wired into rollTarget (shared/state.ts). Updated docs/games/target-range.md's target-placement wording to match (owner-approved, doc added to the story's References). Added a test asserting the per-round cap is monotonic and that rollTarget respects it (test/host/present.test.ts). Regenerated the golden recorded-match fixture (test/recordings/three-player-match.json) from its original input events under the new rule. Independent story-reviewer (sonnet): pass, round 1, no findings. Full verify (check, check:style, check:deps, test, build) green locally and in CI, including e2e.
